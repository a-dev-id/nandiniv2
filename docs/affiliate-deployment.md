# Affiliate subdomain deployment

The Partner Circle runs from this Laravel application and the existing database. Do not deploy it to a separate directory or Laravel installation.

Production requires both `affiliate.nandinibali.com` and `go.nandinibali.com` to point to the same server and Laravel `public` directory as `nandinibali.com`. The web server must accept both hostnames, and valid SSL certificates must cover both names. No new domain purchase is required because `go.nandinibali.com` is a subdomain of the existing domain.

Set these production environment values before caching configuration:

```env
AFFILIATE_DOMAIN=affiliate.nandinibali.com
SHORT_LINK_DOMAIN=go.nandinibali.com
SHORT_LINK_SCHEME=https
DISABLE_AFFILIATE_FEATURE=false
AFFILIATE_REGISTRATION_ENABLED=false
SESSION_DOMAIN=.nandinibali.com
SESSION_SECURE_COOKIE=true
TRUSTED_PROXIES=127.0.0.1
AFFILIATE_COUNTRY_HEADER=CF-IPCountry
AFFILIATE_GEOIP_DATABASE=
AFFILIATE_CLICK_HASH_KEY=
AFFILIATE_CLICK_RETENTION_DAYS=395
```

Set `DISABLE_AFFILIATE_FEATURE=true` to temporarily disable the public Affiliate portal and referral short links. Affiliate navigation and footer links are hidden while disabled; internal administration remains available for historical records and outstanding finance work. Clear or rebuild Laravel's configuration cache after changing the value.

Keep `AFFILIATE_REGISTRATION_ENABLED=false` throughout deployment and production smoke testing. This leaves the landing page, Affiliate login, existing Affiliate dashboards, short links, and authorized internal Affiliate creation available while returning a neutral temporary-unavailable page for both registration requests. Set it to `true` only after every launch-critical smoke test passes, then rebuild the configuration cache. This focused switch does not require application maintenance mode.

`TRUSTED_PROXIES` must be replaced with the exact IP addresses or CIDR ranges of the production load balancer, reverse proxy, or CDN connection. Never use `*`. The web server or CDN must overwrite forwarded-IP headers rather than append untrusted client values. The configured country header is accepted only when the immediate network peer matches this trusted list.

`AFFILIATE_CLICK_HASH_KEY` may be left blank to use `APP_KEY`; a separate random application-controlled secret is preferred in production. Changing this key resets same-day visitor matching but does not expose or invalidate historical metrics.

Country detection uses the trusted `AFFILIATE_COUNTRY_HEADER` first. As an optional fallback, `AFFILIATE_GEOIP_DATABASE` may point to a readable local MaxMind country `.mmdb` file. The included `maxmind-db/reader` dependency reads that file locally; the redirect never calls a remote GeoIP API. Country detection must be considered unverified until one of these sources is configured and tested in production.

The confirmed minimum booking-engine destination generated by Part 2 is:

```text
https://nandinijunglebyhanginggardens.reserve-online.net/?voucher={affiliate_code}
```

The centralized URL builder preserves any query parameters already present in the configured `booking_engine_base_url`. It also accepts optional future parameters without putting date-specific defaults in the redirect controller.

Affiliate notifications implement Laravel's queued notification contract and are inserted only after the onboarding or review transaction commits. Production therefore needs a continuously running queue worker and a verified production mail transport. Local development currently queues the notifications and uses the configured log mailer; that does not verify external mail delivery.

## Part 3 click tracking

Run the database migration before accepting short-link traffic:

```bash
php artisan migrate --force
```

The migration creates `affiliate_click_events` and `affiliate_unique_clicks`, adds their reporting indexes and concurrency-safe daily unique constraint, and adds the daily unique-window and 395-day retention settings. Each valid approved redirect stores an exact timestamp, application-timezone reporting date, optional country, coarse device category, normalized referrer host, keyed visitor hash, unique flag, and bot classification.

The schema does not contain plain IP or user-agent fields. IP and normalized user-agent information exist only in request memory while generating the keyed HMAC and resolving an optional local country. Affiliates see aggregate non-bot metrics only. Internal authorized users can see a limited recent-event table that excludes the visitor hash, plain IP, and full user-agent.

The scheduled retention task runs daily at 02:20 application time. Configure the hosting scheduler to invoke Laravel once per minute:

```cron
* * * * * cd /absolute/path/to/project && php artisan schedule:run >> /dev/null 2>&1
```

The cleanup may also be verified manually without changing the configured value:

```bash
php artisan affiliate-clicks:cleanup --retention=395
```

Only use a positive retention value. The command deletes expired raw click events and matching daily unique markers; it does not delete Affiliates, bookings, or other program data. Its log summary contains counts and retention days only, never visitor hashes.

Local development uses `affiliate.nandinibali.test` and the existing shared `.nandinibali.test` session cookie domain. DNS, server virtual-host routing, and SSL remain deployment responsibilities outside Laravel.

```env
SHORT_LINK_DOMAIN=go.nandinibali.test
SHORT_LINK_SCHEME=http
```

When the local DNS tool does not provide wildcard `.test` subdomains, add this entry to the operating-system hosts file with administrator access:

```text
127.0.0.1 affiliate.nandinibali.test
127.0.0.1 go.nandinibali.test
```

The local Apache virtual host must also accept `affiliate.nandinibali.test` and `go.nandinibali.test` (for example, as `ServerAlias` values) and use this project's existing `public` directory, just like the voucher subdomain.

After deploying the updated environment configuration, run `php artisan optimize:clear` (or rebuild the production configuration cache), then confirm:

1. `https://go.nandinibali.com/{affiliate_code}` redirects to the booking engine with the same code in `voucher`.
2. The first non-bot click creates one event and one daily unique marker; a repeat from the same test client on the same day creates another event but no marker.
3. A known preview user-agent still redirects, is marked as a bot, and creates no unique marker.
4. Pending, suspended, rejected, and unknown codes remain unavailable and create no events.
5. A trusted country header resolves only through the configured production proxy. When no trusted header or readable local database exists, country remains `Unknown`.
6. The Affiliate dashboard shows only the signed-in Affiliate's aggregates, and the Filament analytics page is available only to users with `affiliate-click.view`.

Clear or rebuild configuration caches after every proxy, country-source, hash-key, or retention change. A queue is not used in the redirect path, so queue downtime cannot block click recording or the booking redirect.

## Part 4 privacy-safe booking tracking

Part 4 reuses the existing membership booking synchronization. `MembershipBookingApiService` requests the documented internal endpoint at `MEMBERSHIP_API_URL/api/bookings/sync`, and `BookingSyncService` stores each response in `synced_webhotelier_bookings`. After that local record is saved, the same transaction normalizes a guest-free projection and passes it to `SyncAffiliateBookingService`. The Affiliate implementation does not make a second booking-engine request.

Required production configuration remains:

```env
MEMBERSHIP_API_URL=https://membership.nandiniapps.cloud
MEMBERSHIP_API_TOKEN=replace-with-production-token
MEMBERSHIP_API_TIMEOUT=20
BOOKING_SYNC_CRON_TOKEN=replace-with-a-long-random-token
```

Invoke the existing protected sync URL on the hosting schedule already used by the project:

```text
https://nandinibali.com/cron/bookings/sync/{BOOKING_SYNC_CRON_TOKEN}
```

The endpoint uses an application lock and a 48-hour update overlap. Affiliate projections use `source_system + external_booking_id`, a safe data fingerprint, and `source_updated_at` stale-event protection, so overlap and API retries update or leave the same booking rather than create duplicates. The response contains a count by Affiliate synchronization result. No queue is required for the projection, and no per-booking email is sent.

The migration creates `affiliate_bookings` and `affiliate_booking_rooms`. Both tables contain attribution, dates, room details, normalized statuses, provisional commission data, synchronization timestamps, and fingerprints only. They have no guest name, email, phone, address, IP, payment, notes, special-request, or raw-payload fields. Existing sensitive booking records are referenced by nullable local ID and are never copied into the Affiliate tables.

Multiple rooms use one child record per stable source room identifier. When an identifier is absent, ingestion generates a deterministic line identifier. Repeated synchronization uses that identifier to update existing lines and remove obsolete ones. Stay nights always come from check-out minus check-in; a source nights mismatch becomes a non-sensitive warning.

Voucher matching trims and lowercases the confirmed source `voucher_code` value, then requires one exact `affiliate_code` match. Missing, unknown, partial, and ambiguous values are skipped and summarized in safe logs. New bookings returned with a pending, rejected, or suspended Affiliate code are retained for internal review with an attribution warning. Existing historical attribution is never reassigned merely because Affiliate status later changes.

Source statuses are mapped centrally:

- `reserved`, `confirmed`, `booked` → `confirmed`
- `checked_in`, `checkedin`, `inhouse`, `in_house` → `in_house`
- `checked_out`, `checkedout`, `completed`, `departed` → `completed`
- `cancelled`, `canceled` → `cancelled`
- `no_show`, `noshow` → `no_show`
- `refunded`, `fully_refunded` → `refunded`
- all other safe normalized values → `unknown`

The membership API's `room_subtotal` field is the only commission revenue base accepted by the booking synchronization path. `booking_total` remains stored for booking context but is never used as a commission fallback because it may include extras, fees, or taxes. Payloads without `room_subtotal` show `Pending calculation`. Valid room subtotals are normalized and used to calculate commission with BCMath in the same currency. The configured percentage (currently 10.00%) is snapshotted on first attribution; later global setting changes do not alter that booking automatically. Confirmed and in-house stays are `estimated`, completed stays are `pending_validation`, cancelled/no-show/refunded stays are `ineligible` with zero commission, and unknown or unverified calculations are `calculation_unavailable`.

The approved Affiliate dashboard shows only room type, stay length, check-in, check-out, and estimated commission or eligibility text. Its summary uses database aggregation for tracked bookings, room nights, and separate commission totals per currency. It never shows booking references, revenue, booking source, guest identity, payment information, or other Affiliates' records. Pending, rejected, and suspended Affiliates do not receive booking data.

Authorized Sales & Marketing and Finance users with `affiliate-booking.view` can use the read-only **Affiliate Bookings** Filament resource. It includes internal opaque reference, normalized room revenue, source, warnings, status, commission estimate, and synchronization details, but no guest fields. Corrections must arrive through synchronization; create, edit, and delete operations are disabled.

After migration, an existing local-booking backfill may be run without contacting the remote source:

```bash
php artisan affiliate-bookings:sync-existing
```

Use `--id={synced_webhotelier_booking_id}` to process one local record. Because the same ingestion service and unique identity are used, the command is safe to repeat. An automatic source exists, so Part 4 intentionally does not add the manual CSV fallback.

Production verification:

1. Run `php artisan migrate --force` and `php artisan optimize:clear`.
2. Confirm the protected booking sync can authenticate to `membership.nandiniapps.cloud` and returns `voucher_code`, stable booking number, dates, room information, status, currency, and update timestamp.
3. Trigger a confirmed test booking with an approved code and confirm one privacy-safe projection is created.
4. Repeat the same response, then send a newer modification and an older stale response; confirm the record is unchanged/updated/stale-ignored respectively.
5. Verify completed, cancelled, no-show, and refunded states and inspect safe Affiliate audit entries.
6. Inspect both Affiliate booking table schemas and the public dashboard for the privacy exclusions above.
7. Verify the booking resource as Administrator, Sales & Marketing, Finance, and an Affiliate account.

The application-side automatic hook is implemented, but production automatic synchronization must not be considered verified until the production membership endpoint, token, hosting cron, and returned voucher/room fields have been tested successfully. Direct external WebHotelier access is not required by this projection while the internal membership source remains authoritative. Monthly commission validation, approval, adjustments, payout batches, bank/Wise details, currency conversion, and payment notifications remain intentionally postponed to Part 5.

## Affiliate landing-page finalization

The public Affiliate landing page reuses the main website layout, navbar, footer, Inter and Unna typography, shared buttons, responsive breakpoints, gold/slate palette, and the existing `images/membership/join-today.webp` resort image. Commission and guest-discount percentages are rendered from `affiliate_program_settings`; they are not duplicated as fixed Blade configuration.

The page links to the existing named registration and login routes and replaces registration prompts with **Go to Dashboard** only when the signed-in web user has an Affiliate profile. Member authentication remains on the separate member guard, and internal users without Affiliate profiles are never shown an Affiliate dashboard action.

The real local database currently has an inactive `privacy-policy` page and no active general Terms and Conditions page. The landing page therefore does not create links to invalid or incomplete legal destinations. Activate reviewed general policy pages or add finalized Affiliate-specific terms in a future legal-content step, then add those valid routes near the registration calls to action. This legal-content limitation does not block the landing-page launch.

The landing page describes monthly payouts as a program benefit for qualified completed stays only. It does not imply that Laravel transfers funds. Finance validation and manual payout recording are implemented in Part 5; external payment execution remains outside this system.

## Part 5 commission validation and manual payout recording

Part 5 adds `affiliate_commission_periods`, `affiliate_commission_items`, `affiliate_payment_profiles`, `affiliate_payout_minimums`, `affiliate_payout_number_sequences`, `affiliate_payouts`, and `affiliate_payout_items`. It also adds validation-window settings and renames the earlier `payment_release_days` setting to `payout_release_days`. Run the migrations before seeding permissions or using Finance screens:

```bash
php artisan migrate --force
php artisan db:seed --class=AffiliateFoundationSeeder --force
php artisan optimize:clear
```

`APP_KEY` is mandatory and must remain stable because Wise email, account-holder, bank, account-number, country, and SWIFT/BIC fields use Laravel encrypted casts. Back up the production key securely before deployment. Rotating or losing the key without configuring `APP_PREVIOUS_KEYS` makes existing encrypted payment details unreadable. Never copy production payment values into fixtures, logs, tickets, exports, or documentation.

The application timezone controls completion months, the previous-month default, payment dates, and the scheduled validation window. Production should use:

```dotenv
APP_TIMEZONE=Asia/Makassar
QUEUE_CONNECTION=database
```

Run monthly preparation manually with:

```bash
php artisan affiliate:prepare-commissions
php artisan affiliate:prepare-commissions --year=2026 --month=7
```

Without options the command prepares the previous calendar month. It is idempotent and creates only pending-review snapshots for completed, pending-validation stays using check-out date. It never approves a commission, finalizes a period, creates a paid payout, or sends money. The scheduler checks daily at `02:40` in the application timezone and runs during the configurable `commission_validation_start_day` through `commission_validation_end_day` window. Configure the hosting cron to invoke `php artisan schedule:run` every minute and use `php artisan schedule:list` to verify it.

Commercial settings are available under **Affiliate System → Program Settings**. The seeded validation window is days 1–7 and `payout_release_days` is 30. These guide timing and overdue indicators but do not block late manual processing. Currency thresholds are managed under **Affiliate Finance → Payout Minimums** and are linked from Program Settings. IDR is seeded at 500,000. No other currency inherits that threshold, and no currency conversion occurs. Missing thresholds leave approved items carried forward with a Finance-setup notice.

Finance role access includes commission viewing, validation and approval, encrypted payment-profile review, payout viewing and management, payout-minimum configuration, and Finance timing configuration. Sales & Marketing cannot open payment-profile or payout pages and cannot decrypt payment values. Affiliate accounts remain blocked from Filament and may update only their own profile through `/payment-details` while approved.

Finance prepares a period, explicitly approves, holds, or excludes each item, and finalizes only when no pending-review items remain. Held items remain unpaid. Reopening requires a documented reason and is blocked when a period contains paid items. Source changes update pending snapshots, return reviewed unlocked items to review, and create discrepancy warnings rather than changing included or paid values.

Payout preparation groups finalized, approved, unpaid items by Affiliate and currency, includes prior carried balances, checks the active threshold and complete payment profile, and snapshots only masked payment details. Payout numbers use a transactionally locked yearly sequence such as `AFF-PAY-2026-00001`. Finance then uses explicit **Mark Ready**, **Start Processing**, **Mark Paid**, **Mark Failed**, or **Cancel Payout** actions. Mark Paid requires a date and external reference. Cancellation preserves the payout record and audit history while releasing unpaid commission items.

Payout-paid email notifications are queued after the database transaction commits. A production queue worker is therefore required, for example:

```bash
php artisan queue:work --tries=3 --timeout=90
```

The notification contains only payout number, amount, currency, method, payment date, and the Affiliate dashboard link. It does not contain full Wise or bank details. No automatic failed-payout message is sent.

All payment-profile database columns containing personal payment values are encrypted. Affiliate and general Finance tables use masked details, and only the permission-protected Finance detail page decrypts them. Finance audit metadata records IDs, states, amounts, methods, documented workflow reasons, and masked snapshots only. It excludes guest identity, booking payloads, full emails, full account numbers, ciphertext, passwords, tokens, IP addresses, and user agents. General Affiliate exports must continue to exclude payment details.

Production verification checklist:

1. Confirm `APP_KEY`, `APP_TIMEZONE`, database queue, queue worker, and per-minute scheduler cron before migration.
2. Run migrations and the foundation seeder, then confirm IDR 500,000 and the validation/release settings with Finance.
3. Prepare the previous month twice and confirm the second run creates no duplicate commission items.
4. Confirm cancelled, no-show, refunded, unavailable-calculation, and already-prepared bookings are excluded safely.
5. Approve an unchanged amount, approve a documented adjustment, hold with a reason, exclude with a reason, and verify the audit history contains no guest or payment values.
6. Confirm pending items block finalization, held items may remain, and paid history blocks reopening.
7. Save synthetic Wise and international bank profiles, inspect raw database values to confirm encryption, and verify Affiliate masking, Finance detail access, and Sales denial.
8. Verify an IDR 300,000 balance carries forward; add IDR 250,000 and confirm one IDR 550,000 draft payout. Verify a different currency remains separate and requires its own threshold.
9. Move a synthetic payout through ready, processing, and paid with an external reference; confirm linked items become paid and one queued notification is dispatched after commit.
10. Cancel a separate unpaid payout and confirm its items return to approved while the cancelled payout and audit events remain.
11. Confirm dashboards and tables contain no guest details, room revenue on the Affiliate side, unmasked payment data, raw payloads, click IP, or click user agent.

The local-only `AffiliateFinanceDevelopmentSeeder` supplies synthetic periods, decisions, Wise and bank profiles, missing-profile and missing-threshold cases, carry-forward balances, and every payout status. It is called only by the local `DatabaseSeeder` branch.

This implementation does not call Wise, a bank, a card processor, an exchange-rate provider, or an automatic payment-confirmation service. Finance completes payment externally and records the result manually. Tax calculations, invoices, government documents, payout correction notes for already-paid history, and automated payment integrations remain postponed beyond Part 5.

## Part 6 operations and production launch checklist

Part 6 adds private Affiliate marketing assets, approved-Affiliate reports and CSV exports, permission-scoped internal reports, central program settings, operational state heartbeats, and an Affiliate System Health page. Marketing files are stored on the private `local` disk and delivered only through authorized routes. Direct video uploads are intentionally disabled; use an approved HTTPS video URL. Uploaded images accept JPG, PNG, or WEBP, documents accept PDF, and the application generates the storage path.

The final Filament navigation is grouped as **Affiliate Management** (Affiliates, Affiliate Bookings, Click Analytics, Marketing Assets, Reports), **Affiliate Finance** (Finance Overview, Commission Periods, Commission Validation, Payment Profiles, Affiliate Payouts, Payout Minimums), and **Affiliate System** (Program Settings, System Health). Each item remains permission-scoped; Sales & Marketing does not receive payment-profile or payout access, and Finance does not receive marketing-asset management.

Operational report filters are applied server-side to the matching summaries and CSV exports. Export values are UTF-8 with a BOM and values beginning with `=`, `+`, `-`, or `@` are prefixed safely before CSV encoding. Affiliate exports always resolve the signed-in Affiliate and never accept an Affiliate ID. Branded Affiliate error responses cover restricted portal pages and unavailable protected resources without exposing record existence or exception details.

System Health reports configured Affiliate and short-link domains as **Unknown** until DNS, routing, SSL, and redirect behavior are externally verified. Queue configuration and dispatch records do not prove a worker is running. Scheduler health uses the recorded heartbeat; click cleanup and commission preparation also require a recent successful operational-state record.

Before public launch, complete and record every item below. An application check marked configured is not proof that external infrastructure works.

### Domains, DNS, server routing, and SSL

- Point `affiliate.nandinibali.com` and `go.nandinibali.com` to the production server.
- Configure Apache, Nginx, or the hosting control panel so both names use the same Laravel `public` directory as `nandinibali.com`.
- Issue and verify valid SSL certificates for both subdomains.
- Test the Affiliate portal and a real approved short-link redirect over HTTPS.

### Deployment commands

From the production project directory, use the deployment mechanism appropriate to the host. A typical release is:

```bash
composer install --no-dev --optimize-autoloader
php artisan migrate --force
php artisan db:seed --class=AffiliateFoundationSeeder --force
npm ci
npm run build
php artisan optimize:clear
php artisan config:cache
php artisan route:cache
php artisan view:cache
php artisan migrate:status
php artisan schedule:list
```

Do not run `composer setup` or `php artisan key:generate` during production deployment. The Composer `setup` and project-creation scripts are development bootstrap conveniences and intentionally generate a key for a new installation; they are not release commands for an existing environment with encrypted data.

`AffiliateFoundationSeeder` is the required idempotent production seeder for roles, permissions, the singleton settings record, and the initial IDR threshold. `AffiliateDevelopmentSeeder`, `AffiliateClickDevelopmentSeeder`, `AffiliateBookingDevelopmentSeeder`, `AffiliateFinanceDevelopmentSeeder`, and `AffiliateOperationsDevelopmentSeeder` are synthetic local fixtures. Never run them in production. Normal `DatabaseSeeder` invokes them only when `APP_ENV=local`.

### Queue worker and scheduler

Use the host's supported process manager—Supervisor, systemd, or its managed queue-worker feature—to keep `php artisan queue:work --tries=3 --timeout=90` running and restarted after every deployment. Confirm queued Affiliate notifications complete, inspect `failed_jobs`, and retry only after resolving the cause. Notification jobs do not perform financial state transitions.

Configure one cron entry, with the actual production path substituted:

```cron
* * * * * cd /absolute/path/to/project && php artisan schedule:run >> /dev/null 2>&1
```

The Asia/Makassar Affiliate schedule is:

- every five minutes: `affiliate:heartbeat`
- daily 02:20: `affiliate-clicks:cleanup`
- daily 02:40 during the configured validation days: `affiliate:prepare-commissions`
- booking synchronization: the existing protected hosting schedule; do not add a duplicate Laravel schedule unless the deployment model changes

Verify `php artisan schedule:list`, wait for a heartbeat, then inspect **Affiliate System → System Health**. Run the cleanup and commission commands twice with synthetic data when validating idempotency.

### Backup and rollback safety

Before deploying, back up the database, current environment configuration, stable `APP_KEY`, and private Affiliate asset directories. Record `php artisan migrate:status` and confirm a restorable database backup. Do not copy secrets into the release archive.

For rollback, restore application code and compatible cached configuration together, restart queue workers, and keep uploaded asset directories aligned with their database records. Database migration rollback must be assessed against real data before execution. Never delete commission, payout, or paid history to simulate a rollback. Preserve encryption compatibility throughout.

### Launch decisions and external verification

- Finance must confirm the commission percentage, guest discount, validation window, release days, each currency minimum, and payment methods.
- Test the booking API with real production credentials and confirm `voucher_code` is present without logging guest payloads.
- Test queue execution, scheduler heartbeat, booking sync, country detection, storage downloads, and mail delivery in production.
- Confirm every production role and permission assignment.
- Review report and export samples for privacy and spreadsheet safety.
- Obtain approved Affiliate-specific terms and privacy wording from the business or legal reviewer. The application does not invent those documents.

Until DNS, SSL, queue workers, scheduler, booking API access, mail delivery, Finance configuration, and legal wording are verified, the application implementation may be complete and locally tested but the Affiliate program must not be described as production-ready.
